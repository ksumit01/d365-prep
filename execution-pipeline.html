You hit Save on a new Account. What actually happens?

Between the click and "record saved", your data crosses two worlds — the browser and the server — and runs through a staged event pipeline wrapped in a database transaction. Every plugin, business rule, workflow and flow fires at a precise point. This page walks the whole path, with a simulator for the three outcomes that matter.

The one rule to anchor everything: synchronous work (pre/main/post-operation) shares one transaction — if any of it throws, the record is never created. Asynchronous work runs after commit, so its failure can't undo the save.

The two worlds

Half of your logic runs before anything is sent (in the browser), and half runs on the server. Knowing which is which explains most "why did/didn't this fire" questions.

Client-side (browser) — a gatekeeper. As you fill the form, form-scoped Business Rules show/hide/lock/require fields. When you click Save, OnSave JavaScript (your web resources) runs and can call preventDefault() to cancel the save — if it does, nothing reaches the server. This layer never touches the database; it only decides whether the request is sent.

Server-side — the pipeline. The server receives one Create message and runs it through staged events, with a transaction wrapping the core. That's the simulator above.

The transaction rule — what rolls back what

Pre-validation is outside the transaction. Pre-op → Main → Post-op (sync) all share one transaction.

  • If any synchronous step throws → the whole transaction rolls back → the Account is never created, and the user sees the error. (Simulator: "Sync plugin throws".)
  • Async steps run after commit in their own transactions. If one fails, the Account still exists — only the background job fails, visible in System Jobs (AsyncOperation). (Simulator: "Async job fails".)
A validation that must block a bad Account → synchronous. A "push to billing system" → async, so a flaky API can't roll back the user's save.

Deep dives
Business Rules — client scope vs entity scope

Scope = Form (specific form or All Forms): runs client-side only — generated JavaScript. Show/hide, lock, set value, recommend, require. Not enforced on the server.

Scope = Entity: runs on the server too, synchronously (like a pre-operation step), and on the client. This is the key detail — entity-scoped rules are enforced even when the write comes from an integration or the API, not just the form.

Why Power Automate fires "after", not during

A Dataverse-triggered flow is wired through a post-operation step that, after the transaction commits, notifies the Flow service. The flow then runs asynchronously, with some latency.

Consequences: a flow can't block or roll back the user's save, and it sees the record only after it's committed. If you need to stop a bad save, that's a synchronous plugin, not a flow.

Same record edit → Pre-op, not Post-op

To set a field on the record being saved, edit the Target in a Pre-operation step — the value is written with the original operation, no second update, no recursion.

Calling service.Update() on the same record from Post-op re-triggers the pipeline and can hit the depth limit (default 8) → the loop error. "Modify this record" = Pre-op edit the Target; "react and touch other records" = Post-op.

Reading old values — Pre-Image

On Update, the Target holds only the changed fields. To read an old or unchanged value, register a Pre-Image and read context.PreEntityImages — cheaper than a Retrieve. Pre-Image: Update/Delete. Post-Image: Create/Update.
