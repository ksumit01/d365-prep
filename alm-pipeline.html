You build in one place. The customer runs in another. How does a change travel safely?

That journey is ALM. You work in Dev, package your work into a solution, and import it into Test then Prod — repeatably, without breaking what's live. Press the buttons below and watch a change flow down the pipeline.

The rule everything rests on: you only edit Dev. Test and Prod never get hand-edited — they receive imports. And you develop unmanaged, but you ship managed.

The deep pieces
Publisher & prefix — why avpx_ / av_

Every solution has a publisher, which stamps a prefix on everything you create — a namespace so your components never collide with Microsoft's or another ISV's.

PREXA365: avpx_ and av_ are two publishers/solution lines across your client environments. Enterprise: a firm sets one publisher per vendor/team so ownership is always legible.

Set the publisher before you build — you can't change a component's prefix afterwards.

Environment variables & connection references

Some values differ per environment. You never hard-code them — you make them rebindable so the same managed solution works everywhere:

  • Environment variables — values that change per env (an API URL, a config flag). Ship the variable in the solution; set its value per environment.
  • Connection references — which connection a Power Automate flow uses, so the flow isn't bound to your personal connection. Point it at the right connection in each env.
PREXA365: the billing-API URL is an environment variable — Dev points at the sandbox API, Prod at the live one, same solution. The invoice flow uses a connection reference so it runs as a service account in Prod, not your login.
Upgrade vs Update vs Patch (holding solutions)

Three ways a managed solution version replaces the old one:

  • Upgrade (recommended) — imports the new version and deletes components removed since the last version. Cleanest; keeps Prod tidy.
  • Update / Stage for upgrade — like upgrade but you control when the old version is removed (two-step), useful to minimise downtime.
  • Patch — a small additive delta on top of a base version; fast to ship a hotfix, but patches don't delete anything and pile up until you roll them into the base.
Rule of thumb: normal releases → Upgrade. Urgent hotfix → Patch, then fold it back into the base later.
How you actually deploy
  • Manual — export the managed .zip from Dev, import into Test/Prod. Fine for small teams; error-prone at scale.
  • Power Platform Pipelines — built-in Dev→Test→Prod promotion in the maker portal, with approvals. Low-code, no Azure DevOps needed.
  • Azure DevOps / GitHub — the Power Platform Build Tools export, pack and import solutions in a CI/CD pipeline; source control holds the unpacked solution. This is where your signed plugin assembly flows too.
Your world: across many client environments, pipelines (or scripted DevOps) keep each client's Prod in sync with a tested managed build — no hand edits in Prod.
Common traps
  • Editing Prod directly → creates an unmanaged (Active) layer that overrides your managed import — your next release "won't show up" (Solution Layering page).
  • Shipping unmanaged to Prod → no clean upgrade or rollback.
  • The default "Common Data Services Default Solution" → building there dumps everything in one bucket with the default publisher. Always build in your own named solution with your publisher.
  • Hard-coding URLs/GUIDs → use environment variables / connection references instead.
Say it in one breath
Build unmanaged in Dev inside your own solution with your publisher prefix, ship it managed into Test then Prod (never hand-edit Test/Prod), rebind per-environment values with environment variables and connection references, and release with Upgrade (Patch for hotfixes) through pipelines — so every environment is reproducible and rollback is clean.
